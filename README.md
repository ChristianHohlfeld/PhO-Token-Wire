# PhO Token Wire

**Client-side token reduction for LLM web chats — by Christian Heinrich Hohlfeld.**

**Author / concept:** Christian Heinrich Hohlfeld, B.Sc.  
**ORCID:** [0009-0003-6634-9045](https://orcid.org/0009-0003-6634-9045)  
**Website:** [christianhohlfeld.com](https://christianhohlfeld.com/)  
**Research lineage:** [PhO-Compress — A Two-Stage Framework to Enhance Optical LLM Context Compression](https://christianhohlfeld.com/Christian_Heinrich_Hohlfeld_Konstanz_PhO-Compress_v2.pdf)

PhO Token Wire is a Chrome Manifest V3 extension that reduces the amount of text sent to and generated by LLM web chats while keeping the browser-facing result readable. The project follows a central distinction from Hohlfeld's PhO-Compress research direction: **first reduce redundant information; only then optimize the representation used on the transport channel.**

The extension therefore does **not** assume that fewer characters automatically mean fewer model tokens. Every input transformation is measured against the original prompt with an `o200k_base` tokenizer implementation. If the transformed prompt is not cheaper in that encoding, the original prompt is retained.

## Core idea

A normal web-chat path looks roughly like this:

```text
human language -> tokenizer -> model -> verbose human language
```

PhO Token Wire inserts a client-side semantic layer:

```text
human prompt
  -> conservative redundancy reduction
  -> tokenizer-cost check
  -> compact semantic wire instruction
  -> LLM
  -> K/F/U/N payload
  -> local browser decoder / renderer
  -> readable answer
```

The important separation is:

1. **Information layer:** decide which information is actually necessary for the task.
2. **Transport layer:** represent that information in strings the existing model/tokenizer handles efficiently.
3. **Presentation layer:** restore labels and readable structure locally in the browser, where those words cost no LLM completion tokens.

This is deliberately different from sending IPA, Base64, arbitrary Unicode symbols, or numeric vectors and hoping that a standard BPE tokenizer will make them cheap. Such representations can contain fewer characters while consuming more tokens.

## What actually saves tokens

### 1. Input compression

The extension performs conservative deterministic rewrites outside protected regions. It protects code blocks, inline code, URLs, email addresses, long IDs and similar literals, then removes selected redundant phrasing and conversational filler.

Before replacing the prompt, it compares the transformed string with the original using `o200k_base`. **The compressed input is only used when the measured text-token count is lower.**

Examples of safe normalization include:

```text
"aufgrund der Tatsache, dass" -> "weil"
"in order to"                -> "to"
"zum Beispiel"               -> "z.B."
```

The goal is not stylistic minimalism by itself; the acceptance criterion is lower token cost without intentionally changing the requested task.

### 2. Completion compression

Most assistant answers spend tokens on presentation: introductions, repeated context, headings, connective prose and conclusions. PhO Token Wire asks the model to return a compact semantic payload instead:

```text
K:Race Condition beim Replay
F:Click feuert vor Dropdown|kein await auf sichtbaren Zielzustand
U:Browser-Timing variiert
N:vor Click auf sichtbar+enabled warten
```

The browser renders that locally as readable sections such as **Kern**, **Fakten**, **Unsicherheit**, and **Nächster Schritt**. The labels and HTML structure are produced by the extension, not by the model, so they do not consume completion tokens.

The protocol fields are:

- `K` — core result / conclusion
- `F` — compact facts, separated by `|`
- `U` — only decision-relevant uncertainty
- `N` — next action

Empty fields are omitted.

### 3. Why this is not an IPA/BPE trick

PhO-Compress motivates separating linguistic redundancy from the later transport or optical representation. PhO Token Wire applies that principle to today's unchanged web-chat models, but does not claim that literal IPA is automatically token-efficient.

A tokenizer charges for token IDs, not letters. Therefore:

```text
fewer characters != fewer tokens
```

A phonetically shorter string can fragment into many rare BPE pieces. The extension's current implementation avoids that failure mode: semantic reduction and transport encoding remain separate concerns.

## Relationship to PhO-Compress

PhO Token Wire is an applied browser-side experiment derived from Christian Heinrich Hohlfeld's broader PhO-Compress research direction.

PhO-Compress proposes a two-stage architecture in which linguistic redundancy is reduced before a later compression/representation stage. The Chrome extension targets a narrower engineering question:

> How much context and completion overhead can be removed around an unchanged hosted LLM, without changing the model itself?

The current extension is therefore **not a complete implementation of the PhO-Compress paper**, and it does not claim orthographically lossless phonetic reconstruction. It is a practical transport-layer prototype that applies the same first-principles separation of information, encoding and presentation.

## Installation

1. Download or clone this repository.
2. Open `chrome://extensions`.
3. Enable **Developer mode**.
4. Click **Load unpacked**.
5. Select the repository folder.
6. Reload ChatGPT, Claude, Gemini or Grok.

A **PhO Token Wire** control appears in supported chats. Write a prompt, select **Komprimieren + Wire**, inspect the token comparison, then send normally.

## Supported web chats

The current content script targets:

- ChatGPT (`chatgpt.com`, legacy `chat.openai.com`)
- Claude (`claude.ai`)
- Gemini (`gemini.google.com`)
- Grok (`grok.com`)

These are DOM integrations, not official provider plugins. Web interfaces can change and may require selector updates.

## Token measurement

The service worker downloads and caches OpenAI's public `o200k_base.tiktoken` rank table from:

```text
https://openaipublic.blob.core.windows.net/encodings/o200k_base.tiktoken
```

The extension implements local segmentation and BPE counting and runs self-tests against known `o200k_base` examples before reporting an exact count. If the tokenizer data cannot be loaded, the UI falls back to a clearly marked estimate.

What the extension can measure:

- visible prompt text before transformation
- visible prompt text after transformation
- the text-token delta in `o200k_base`

What it cannot measure from a browser page:

- provider system prompts
- hidden conversation framing
- tool-call tokens
- cached-token accounting
- model-specific internal tokenization when it differs from `o200k_base`
- invisible reasoning or provider-side processing

Accordingly, the project reports **text-token savings on the measured transport text**, not a guaranteed provider billing reduction for every model or product.

## Architecture

```text
manifest.json
  Chrome MV3 declaration, supported hosts, author metadata

compressor.js
  protected-span handling
  deterministic prompt reduction
  language detection
  K/F/U/N wire instruction
  local wire parser and renderer

tokenizer.js
  o200k_base rank loading/cache
  local BPE token counting
  self-test vectors
  fallback estimator

background.js
  service-worker bridge for token counting and settings

content.js
  web-chat composer discovery
  before/after token comparison
  prompt replacement
  response detection and local decode

popup.html / popup.js
  user settings

tests/test_compressor.js
  deterministic compressor tests
```

## Safety properties of the current compressor

The current implementation intentionally favors conservative transformations. Before generic text normalization it protects:

- fenced code blocks
- inline code
- URLs
- email addresses
- long hexadecimal identifiers
- long numeric identifiers

It also avoids replacing the prompt when the transformation fails the token-cost gate.

This does **not** prove semantic equivalence for arbitrary natural language. Aggressive mode can remove nuance and should be treated as an experiment.

## Privacy

Prompt compression and wire decoding happen locally in the browser. The extension does not require its own application server.

The only network resource requested by the extension itself is the public tokenizer rank table used for token measurement. The actual chat prompt still goes to the LLM provider selected by the user, exactly as it would without the extension.

## Testing

Run the compressor tests with Node.js:

```bash
node tests/test_compressor.js
```

For a meaningful token-saving evaluation, test a corpus of real prompts and record at least:

```text
input_tokens_original
input_tokens_transformed
output_tokens_normal
output_tokens_wire
semantic_success_rate
wire_parse_success_rate
```

Useful aggregate metrics are:

```text
input_saving  = 1 - transformed/original
output_saving = 1 - wire/normal
total_saving  = 1 - (transformed + wire)/(original + normal)
```

The important result is not character reduction but task-equivalent information delivered per paid/processed token.

## Current limitations

- `o200k_base` is a measurement basis, not a universal tokenizer for every provider.
- A browser extension cannot reliably set server-side `max_tokens` / `max_output_tokens` in third-party web products.
- Completion reduction is instruction-driven; a hosted model can ignore or partially follow the wire protocol.
- Long-form writing, code generation and reusable artifacts should not be forced through the tiny wire schema.
- The current input compressor is phrase-based, not a full phonetic PhO encoder.
- DOM changes at supported providers can break composer or response detection.

## Research questions / roadmap

The most important next experiments are empirical:

1. Measure savings over a representative multi-provider prompt corpus.
2. Learn a tokenizer-aware compact semantic alphabet from already-atomic/high-frequency tokens.
3. Compare prompt-only semantic pruning against phonetic/phonotactic reduction with a protected side channel.
4. Quantify task fidelity versus token reduction rather than character reduction.
5. Add provider-specific tokenizers where their vocabulary is known.
6. Evaluate whether a deterministic browser rehydrator can reconstruct more natural presentation without sending those presentation tokens through the LLM.
